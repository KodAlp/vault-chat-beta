# Study Artifacts

Turns retrieved library content into verifiable study material. Two
artifact types are mandatory and specified here: **quizzes** and
**knowledge cards**. Mind maps / reports / slides reuse the same pattern
later (see "Extending" at the end).

## Grounding rule (the whole point)

Every generated item MUST reference real source chunks obtained through
`retrieve()` (see `vault-rag-index`). Generation without retrieved context
is forbidden: if retrieval returns empty for the requested scope, the UI
says so ("Bu konu için kütüphanede yeterli kaynak yok") instead of letting
the model invent questions. Each item stores `source_path` +
`heading_path`; the review UI renders them as `obsidian://` /
in-app-library links. This is the local equivalent of NotebookLM's
source-pinned answers and it is not negotiable.

## Generation pipeline (shared by all artifact types)

1. **Scope selection.** The action buttons operate on one of:
   (a) selected node(s) in the left library tree, (b) a `domain` filter,
   (c) the current chat's last N messages as topic seed. Scope → a
   retrieval query set (3–6 queries generated by the model from scope
   titles), then `retrieve()` with `k=12`, deduped.
2. **Structured output.** Call Ollama with `format: "json"` (native
   structured output mode) + an explicit JSON Schema in the prompt.
   Temperature 0.3. The system prompt states: Turkish output, math in
   `$...$` only, every item must include `source_path` copied verbatim
   from the provided context chunks.
3. **Validation.** Parse with `zod` schemas (below). On failure: ONE
   retry with the validator errors appended to the prompt. On second
   failure: surface a readable error, never store partial garbage.
   Reject items whose `source_path` does not match a chunk actually
   provided in context (anti-hallucination check).
4. **Storage.** sqlite (`data/study.db`), WAL mode, same better-sqlite3
   stack as the rest of the app.

## Quiz spec

```ts
const QuizItem = z.object({
  type: z.enum(["multiple_choice", "true_false", "open"]),
  question: z.string(),          // markdown, may contain $math$
  options: z.array(z.string()).length(5).optional(), // MC only — 5, not 4 (user request); UI labels them A)-E)
  answer: z.string(),            // MC: exact option text; TF: "true"/"false"
  explanation: z.string(),       // why, in 1–3 sentences, may cite formula
  source_path: z.string(),
  heading_path: z.string(),
});
```

- Default mix per quiz: 6 MC, 2 TF, 2 open — configurable in the dialog.
- Difficulty is steered by the note's `level` frontmatter; state it in
  the prompt ("bu kaynaklar {level} seviyesindedir, sorular bu seviyede
  olmalı").
- Tables: `quizzes(id, title, scope_json, model, created_at)`,
  `quiz_items(id, quiz_id, ...QuizItem columns)`,
  `attempts(id, quiz_id, started_at, finished_at, score)`,
  `attempt_answers(attempt_id, item_id, given, is_correct, model_feedback)`.
- **Grading:** MC/TF graded in code, never by the model. Open questions:
  the model grades with a rubric prompt (question + reference answer +
  student answer → JSON `{correct: boolean, feedback: string}`), clearly
  labeled in UI as "model değerlendirmesi".
- Quiz UI: one question per screen, progress bar, no answer reveal until
  submitted; results screen shows per-item explanation + source link.
  All question/option/explanation text goes through `renderMarkdown()` —
  math in questions is a first-class requirement.

## Knowledge cards spec

```ts
const ModelCard = z.object({
  front: z.string(),   // prompt side: term / question / formula name
  back: z.string(),    // answer side: definition / derivation sketch
  source_path: z.string(),
  heading_path: z.string(),
});
```

- **Implementation deviation (deliberate):** `domain` and `level` are NOT
  model-supplied fields, unlike the original draft of this spec. Once
  `source_path` passes the anti-hallucination check (matches a chunk
  actually retrieved), `domain`/`level` are derived server-side from
  that chunk's own `domains`/`depth` metadata — same principle already
  applied to `heading_path`. The stored `Card` row still has
  `domain`/`level` columns; they're just populated by the app, not the
  model. See `generate-cards.ts`.
- Card fronts must be *retrieval cues*, not trivia: prefer "Laplace
  dönüşümünün yakınsama bölgesi neyi belirler?" over "ROC nedir?".
  Put this instruction in the generation prompt.
- Tables: `cards(id, deck_id, ...Card columns, ease, interval_days,
  due_at, reps, lapses)`, `decks(id, name, scope_json, created_at)`.
- **Review scheduling:** SM-2 — `again` (interval=0, ease−0.2),
  `hard` (interval×1.2, ease−0.15), `good` (interval×ease, ease unchanged),
  `easy` (interval×ease×1.3 — using the pre-review ease — then ease+0.15);
  ease starts 2.5, floor 1.3, ceiling 3.0; new cards interval 1 day. Ease
  must move in both directions (Faz 11 fix — the original SM-2-lite spec
  only ever lowered it, a one-way ratchet that permanently inflated review
  load for any card mistapped early on). Keep it in one pure function
  `schedule(card, grade)` with unit tests; do not add a dependency for this.
- Review UI: front → self-reveal → 4 grade buttons; daily due count badge
  on the action button. Card faces render through `renderMarkdown()`.

## App integration rules

- New endpoints: `POST /api/generate/quiz`, `POST /api/generate/cards`
  (both SSE: progress events while chunks are retrieved and items
  validated), `GET/POST` CRUD under `/api/study/...`.
- Generation is user-initiated with **visible progress**, but must NOT
  block the UI while it runs (a real generation is 20s-2min — an open
  modal/dialog for that whole span reads as the page being frozen, not
  working; confirmed by direct user feedback). The generation request
  itself lives in a module-level store (`quiz-generation.svelte.ts` for
  quizzes), not tied to any one component/dialog's lifetime, so closing
  the dialog or navigating away doesn't cancel it. A small persistent
  status widget (spinner + stage label while running, a clickable "ready"
  notification on completion, mounted globally so it's visible from any
  route) is the visible-progress requirement — not a blocking overlay.
  Still exactly one user-initiated model call per generation, never a
  hidden/automatic one — the user owns their RAM, just not their screen.
- Model choice: generation defaults to the user's "reasoning" model
  (30B) with fallback to fast model if unavailable; grading of open
  answers may use the fast model.
- Respect user skills (see `user-skills`): scope `quiz` and `flashcards`
  skill files are appended to the generation prompt.

## Extending to mind maps / reports / slides (later phases)

Same pipeline: scope → retrieve → schema-validated structured output →
store → render. Mind map = nested outline JSON rendered with markmap;
report = long-form markdown through the existing renderer; slides = Marp
markdown. Write their zod schemas the same way; do NOT invent a second
generation mechanism.
